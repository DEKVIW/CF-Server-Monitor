# 流量统计方案对比

## 1. 文档目的

本文记录当前 fork 与 CF-Server-Monitor 源项目在流量统计方面的实现差异，方便后续接入第三方主题时继续核对。

本文只讨论流量统计和套餐进度，不讨论主题的视觉样式。

## 3. 两套方案共同点

两套方案都不是直接读取 VPS 服务商后台的数据，而是读取 VPS Linux 内核提供的网卡累计计数器：

```text
/proc/net/dev
```

其中：

- `RX` 表示接收流量，通常对应入站或下载；
- `TX` 表示发送流量，通常对应出站或上传；
- `net_rx_monthly` 和 `net_tx_monthly` 表示探针自己累计的当前账单周期流量；
- `net_rx` 和 `net_tx` 表示探针读取到的网卡生命周期累计计数器。

因此，两套方案都无法保证与 VPS 服务商后台完全相同。服务商可能在宿主机或虚拟交换机层统计流量，并且可能包含协议开销、重传或不同的 NAT 口径。

## 4. 当前 fork 的统计方式

### 4.1 网卡选择

当前 fork 的选择顺序是：

1. 如果后台填写了网卡，优先统计填写的网卡；
2. 如果没有填写，使用：

   ```bash
   ip route get 1.1.1.1
   ```

   获取 IPv4 默认出口网卡；

3. 如果无法获取默认出口，再使用自动匹配和过滤规则；
4. 自动规则优先选择 `eth*`、`en*`、`wl*`、`venet*` 等常见实体或公网网卡；
5. 排除 `docker`、`br-*`、`veth`、`lo`、`warp`、`sit`、`he-ipv6`、`ipv6net` 等虚拟、容器或隧道接口。

这套逻辑适合当前已经确认的机器：公网流量主要从 `eth0` 经过，同时机器上存在大量 Docker bridge 和 veth 接口。

### 4.2 月度流量累计

探针把状态保存到：

```text
/var/lib/cf-probe/traffic.dat
```

主要状态包括：

```text
RX_PREV
TX_PREV
RX_PERIOD
TX_PERIOD
LAST_CHECK
PERIOD_START
```

每次采集时：

1. 读取当前网卡 RX/TX 累计值；
2. 与上一次保存的 RX/TX 值相减，得到本次增量；
3. 将增量加到当前账单周期；
4. 持久化到 `traffic.dat`；
5. 上报 `net_rx_monthly`、`net_tx_monthly` 和 `traffic_period_start`。

如果检测到网卡累计值回退，例如服务器重启或驱动重置，当前这一次增量按 0 处理，避免产生虚假的大流量。之后以新的网卡计数器继续累计。

### 4.3 周期重置

当前 fork 支持：

- `traffic_reset_day`：流量重置日；
- `traffic_reset_tz`：重置日所在时区，默认 `UTC+8`；
- `traffic_period_start`：探针实际计算出的周期起点。

周期判断使用配置的时区，而不是直接使用服务器系统时区或 UTC。这样服务器使用 UTC 系统时间时，仍然可以正确按照北京时间的 15 日零点重置。

### 4.4 Panel Used 校准

后台填写套餐服务商当前显示的已用流量后，当前 fork 会保存：

- `traffic_used_baseline`：服务商后台当前已用总量；
- `traffic_rx_baseline`：校准时探针的 RX 月度计数；
- `traffic_tx_baseline`：校准时探针的 TX 月度计数；
- `traffic_baseline_period_start`：校准时的周期起点。

当前周期未变化时，套餐已用量按以下思路计算：

```text
套餐已用量 = Panel Used + 校准后的周期增量
```

双向统计时：

```text
校准后的周期增量 = (当前 RX - 校准 RX) + (当前 TX - 校准 TX)
```

单向统计时，只使用对应方向的增量。

如果检测到进入新账单周期，旧的 `Panel Used` 自动失效，直接使用新周期的探针累计值，避免旧周期数据继续叠加。

### 4.5 统计模式

当前 fork 使用 `traffic_count_mode`：

| 值 | 含义 |
|---|---|
| `sum` | RX + TX，双向统计 |
| `rx` | 只统计 RX，通常对应入站/下载 |
| `tx` | 只统计 TX，通常对应出站/上传 |

## 5. 源项目的统计方式

### 5.1 网卡选择

源项目支持手动指定网卡。未指定时，主要按名称匹配：

```text
eth*
en*
wl*
```

这对普通单网卡 VPS 通常有效，但它不会优先查询默认出口路由。在存在多块实体网卡、特殊网卡名称、IPv4/IPv6 出口不一致时，当前 fork 的默认出口策略更明确。

### 5.2 月度累计和周期处理

源项目同样使用持久化文件保存上一次网卡计数器和当前周期累计值，遇到计数器回退时避免累加负数。

源项目还会把当前统计网卡写入状态文件。当统计网卡配置发生变化时，会清空旧周期状态，避免不同网卡的计数器直接相减。

这是源项目值得借鉴的一点。

### 5.3 分方向校准

源项目支持分别设置：

- `rx_correction`：RX 校准值；
- `tx_correction`：TX 校准值。

探针收到动态配置后，会将当前周期的 RX/TX 累计值分别重新锚定到校准值，再继续累计。

分方向校准适合服务商后台能够分别显示入站和出站用量的情况。

### 5.4 统计类型

源项目使用 `traffic_calc_type`，常见值包括：

- `total`：上行 + 下行；
- `ul`：只统计上行；
- `dl`：只统计下行；
- `max`：取两者较大值。

这与当前 fork 的 `traffic_count_mode` 不是同一组字段，接入第三方主题时必须做映射，不能直接照搬字段名。

## 6. 哪套方案更接近 VPS 后台

按照当前使用场景，推荐以当前 fork 为主：

1. 当前 fork 会优先识别默认出口网卡；
2. 对 Docker bridge、veth、Warp 和隧道接口过滤更明确；
3. 支持重置日时区，能够正确处理北京时间重置；
4. 已经支持双向、RX 单向和 TX 单向统计；
5. `Panel Used` 适合直接把服务商后台当前显示值作为周期起点校准。

源项目不是统计不准确，而是它的设计重点不同：

- 更接近源项目标准字段；
- 支持分方向校准和动态下发；
- 对网卡配置变化有额外保护；
- 但默认网卡判断和重置时区不如当前 fork 针对本项目场景。

因此，不建议用源项目的整套流量模块覆盖当前 fork。更稳妥的做法是保留当前 fork 的采集和周期逻辑，只参考源项目补充网卡变化保护、分方向校准等独立能力。

## 7. 第三方主题接入注意事项

LuminaPlus 主题只负责读取接口并展示，不会改变探针实际统计结果。

主题主要读取：

```text
net_rx_monthly
net_tx_monthly
traffic_calc_type
traffic_limit
```

当前 fork 接入主题时需要：

1. 保留 `net_rx_monthly` 和 `net_tx_monthly` 的现有含义；
2. 将 `traffic_count_mode` 映射为主题理解的统计类型；
3. 确保 Panel Used 和周期重置后的结果继续由当前 fork 逻辑提供；
4. 不让主题自行重新计算探针周期累计值；
5. 不能因为替换前端主题而丢失单向流量配置。

## 8. 建议的后续改进

后续可以按以下优先级考虑：

### 必须保留

- 默认出口网卡优先；
- 虚拟网卡过滤；
- 手动指定网卡；
- `traffic_reset_tz` 时区计算；
- Panel Used 周期校准；
- 单向和双向统计。

### 可以参考源项目补充

- 在 `traffic.dat` 中记录实际使用的网卡列表；
- 网卡列表发生变化时自动重置探针累计状态；
- 需要时增加 RX/TX 分方向校准；
- 将流量统计算法封装成前后端共用的明确字段。

### 不建议直接引入

- 整体替换当前探针脚本；
- 直接把 `traffic_count_mode` 改成源项目字段；
- 让主题自行计算月度增量；
- 统计 Docker bridge、veth 等虚拟接口来“补齐”流量。

## 9. 手动核对命令

查看所有网卡：

```bash
cat /proc/net/dev
```

查看默认 IPv4 出口网卡：

```bash
ip route get 1.1.1.1 | awk '{for(i=1;i<=NF;i++) if($i=="dev"){print $(i+1); exit}}'
```

查看指定网卡累计计数器，例如 `eth0`：

```bash
cat /sys/class/net/eth0/statistics/rx_bytes
cat /sys/class/net/eth0/statistics/tx_bytes
```

换算为 GiB：

```bash
awk '{printf "%.2f GiB\n", $1/1024/1024/1024}' /sys/class/net/eth0/statistics/rx_bytes
awk '{printf "%.2f GiB\n", $1/1024/1024/1024}' /sys/class/net/eth0/statistics/tx_bytes
```

查看探针周期状态：

```bash
cat /var/lib/cf-probe/traffic.dat
```

## 10. 最终结论

当前 fork 的流量统计方案更适合作为本项目的基础，尤其适合运行 Docker、存在多个虚拟网卡的搬瓦工和 RackNerd VPS。

源项目的分方向校准和网卡变化保护可以作为后续增强点，但不应整体覆盖当前方案。

第三方主题加载工作的重点，是保持现有流量统计结果不变，并正确把当前 fork 的字段转换成主题需要的展示字段。
